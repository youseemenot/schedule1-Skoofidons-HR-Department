# Исследование таймингов ботаника: диагностическая фаза 1

Дата: 30 октября 2026. База — опубликованная HR 1.0.5; исследование ведётся отдельно на ветке codex/botanist-timing-probe. Пользователь задал очередь «исследование → настройки таймингов → адаптивный планшет» и разрешил начать.

**Последующее указание пользователя:** сделать следующие пункты сразу и проверить вместе. Поэтому отдельный наблюдатель0.1.0 снят с установки, а тайминги (выключены по умолчанию) и адаптивный UI включены в [общий кандидат1.1.0-beta.1](2026-10-30-combined-candidate.md). Запись ниже сохраняет результат исходной диагностической фазы, без утверждения о её игровой приёмке.

## Что установлено без запуска игры

GameAssembly.dll по-прежнему соответствует аудиту игры 0.4.7f12 IL2CPP:

`872DFB646C9B866C53DAE12D7A34E1F9DF21A3E16FAC6B7C6CD21BF5FC8E4B3F99932163C5DE7E3798D37641712E82B914D46E1F023D56E77970BE84FB74EC3A`.

Повторный поиск затронул все вложенные типы и все **111** сгенерированных Cpp2IL-сборок, а не только Assembly-CSharp:

| Нативное тело | Все найденные пользователи |
| --- | --- |
| 0x916810 | AddSoilToGrowContainerBehaviour, WaterPotBehaviour, ApplyAdditiveToGrowContainerBehaviour; также callback ProbeReferenceVolume.RegisterDebug и **статический UniversalRenderPipeline.maxShadowBias** |
| 0x917550 | SowSeedInPotBehaviour и ApplySpawnToMushroomBedBehaviour |
| 0x935B90 | HarvestPotBehaviour.GetActionDuration |
| 0x944380 | Только MoveNext coroutine GrowContainerBehaviour.PerformAction |

Изначальная гипотеза перехвата общего GetActionDuration отклонена: нативный trampoline с типом экземпляра ботаника не подходит графическим/static вызовам того же тела. Два отдельных перехвата одного адреса также не решают проблему. Перехваты на GetActionDuration в диагностической DLL отсутствуют.

Выбран предусмотренный планом альтернативный путь: контекстная coroutine PerformAction. Нативный код на первом MoveNext (state=0) вызывает GetActionDuration и CurrentWorkSpeed, записывает `waitTime = baseDuration / CurrentWorkSpeed`, обнуляет `i`, затем возвращает true со state=1. Последующие шаги прибавляют deltaTime к i и сравнивают его с waitTime. После ожидания выполняются штатные действия с ресурсами/растением. Это найденная точка для будущего эксперимента, ещё не доказанный игровой override.

## Диагностическая DLL 0.1.0

Проект: diagnostics/BotanistTimingProbe. Файл: **SkoofidonsHRBotanistProbe.dll**, отдельный от основной HR 1.0.5. Корневой проект компилирует только свои `*.cs`; диагностические файлы в него не входят.

- Один вручную зарегистрированный Harmony target — MoveNext конкретной coroutine; нет HarmonyPatch/PatchAll-деклараций.
- Prefix читает state в управляемый `__state`. Postfix получает bool-результат по значению, читает owner/тип, waitTime, work speed и i. Не пишет в игровые поля, константы, результат MoveNext или Time.timeScale; не вызывает GetActionDuration повторно.
- Сначала проверяет SHA512 игры; неподходящий бинарник оставляет модуль неактивным. Дополнительно проверяются привязки полей/метода, нативный указатель и отсутствие прежних Harmony owners на target.
- START логирует фактический IL2CPP-тип и рассчитанное игрой ожидание, END — накопленное игровое время и реальное время между наблюдениями. `derivedBase = wait * workSpeed`; реальные секунды могут включать паузу, поэтому отдельно записан i.
- Максимум восемь образцов на вид действия за сцену. В трекинге хранятся только управляемые значения, без ссылок на NPC/Unity. Неоконченные записи при остановленной coroutine могут означать отмену; число записей ограничено бюджетом образцов. При выгрузке Main выводится SUMMARY и очищается состояние.
- Земля/вода/удобрение/посев/урожай распознаются отдельно. Грибные и неизвестные действия помечаются other, без изменения поведения.
- Ошибка наблюдения перехватывается и однократно попадает в лог. Ошибка регистрации оставляет основную HR работающей без диагностического патча.

## Проверка в игре

1. При закрытой игре положить только диагностическую DLL рядом с основной HR 1.0.5 в Mods. Игра не запускается агентом автоматически. Удаление диагностической DLL при закрытой игре полностью убирает эксперимент.
2. В свежем Latest.log найти HR **1.0.5**, HR Botanist Timing Probe **0.1.0** и `[BOTANIST_PROBE READY]`. `INACTIVE` или `OBSERVATION ERROR`, исключение trampoline/invalid cast — непрохождение этапа.
3. Дать ботанику выполнить внесение земли, полив и удобрение. Для каждого нужны START с соответствующим kind, правильным nativeType, botanist=True, положительными wait/workSpeed и END после завершения. При штатной базе derivedBase ожидается около 10 для этих трёх действий.
4. По возможности дать ему посеять семя и собрать урожай: ожидаются kind=seed (база около 15) и kind=harvest (база зависит от числа единиц урожая). Проверить, что расход материалов и результат действий остаются обычными. Грибные действия, если доступны, должны остаться штатными и попасть в other.
5. Выйти в меню, получить SUMMARY. Передать свежий MelonLoader/Latest.log с указанием, какие действия фактически выполнялись. Из одного READY нельзя делать вывод о прохождении callback.

После подтверждения наблюдений — отдельная фаза 4A с изменением только экспериментальных времён земли/воды и проверкой остальных действий/отмены/ресурсов. Пользовательские настройки Task 4B и адаптивный UI пока не реализуются: сначала требуется эта игровая проверка.

## Проверки сборки

Управляемые тесты написаны до реализации диагностического протокола. После уточнения механизма проверена окончательная серия: RED 0/16 на базовой HR (диагностического модуля нет), GREEN 16/16 на модуле. В том числе проверены классификация пяти действий, исключение грибов, переход первого ожидания, бюджет логирования, проверка хеша, невмешательство сигнатуры Postfix в результат и JIT-компиляция фактической обёртки MoveNext. Release без ошибок/предупреждений.

Тесты не исполняют Unity или нативный coroutine dispatch. Исследовательские артефакты вне репозитория: artifacts/botanist-probe-2026-10-30/targets.json, all-assemblies.json, исходный disassembly и логи проверок.

Окончательная проверка и установка:

- Ревью без Critical/Important замечаний; отдельно сопоставлены токен MoveNext `0x0600551C`, нативное тело `0x944380` и привязки полей. Minor-риск неверной атрибуции END при переиспользовании адреса отменённой coroutine устранён очисткой старого Pending на каждом state=0 до решения о сэмплировании.
- После этой очистки: повторный Release без ошибок/предупреждений, 16/16 probe checks и 22/22 smoke checks на основной установленной HR 1.0.5.
- Статическая проверка 25 внешних API-ссылок — 0 ошибок. Автоматических Harmony targets — 0, поскольку один target регистрируется явно; его обёртка отдельно проверена JIT-тестом. Это не утверждение об успешной установке detour в игре.
- Проверено отсутствие процесса игры. В Mods добавлена только SkoofidonsHRBotanistProbe.dll 0.1.0, SHA256 `58709996B3C05511A03A873A3982CF8E157E957D21BC58D7A567D96181F1EFFE`.
- Основная HR 1.0.5 не заменялась: её SHA256 по-прежнему `6D293EE64D743B688F4CD0DB3C9BED52CD6A4A9F7FFA2D84C10B010949CC1101`. Дополнительная резервная копия находится вне Mods: artifacts/hr-backups/2026-10-30/SkoofidonsHRDepartment.v1.0.5.6D293EE6.dll.

- Фаза исследования ожидает первый игровой лог. На этом этапе нельзя утверждать, что hook уже отработал на NPC, что override времени проверен или что Task 4A/4B завершены.
