# HR unfinished singleplayer features — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement the accepted stage task-by-task. This document is a proposed roadmap; no feature implementation is authorized by its checkboxes alone.

**Goal:** Последовательно восстановить нереализованные функции HR, сохраняя рабочую одиночную базу и проверяя каждый результат.

**Architecture:** Типизированные UI-компоненты, переопределения изменяемых параметров недвижимости, отдельный эксперимент для расчёта длительности действий ботаника. Никаких записей в игровые константы или глобального изменения времени игры. Каждый этап — отдельное изменение с возможностью отката; не объединять их в один большой патч.

**Tech Stack:** C# 11, .NET 6, MelonLoader 0.7.3, Harmony, Schedule I 0.4.7f12 IL2CPP, Phone App 2.2.4.

**Spec:** [Исследование, альтернативы и проект](../specs/2026-10-30-unfinished-features-research.md).

**Очередь, заданная пользователем 30 октября 2026:** **5 → 6 → 4** из краткого плана в чате: исследование таймингов ботаника → настройки таймингов ботаника → адаптивная компоновка планшета. В технических разделах ниже это **Task 4A → Task 4B → Task 3**; номера сохранены для существующих ссылок. Лимиты сотрудников недвижимости (Task 2) остаются в бэклоге вне ближайшей очереди.

**Уточнение пользователя после диагностической сборки:** реализовать следующие пункты сразу и проверить их вместе. По этому прямому указанию последовательный игровой допуск 4A→4B→3 заменён общей приёмкой [комбинированного кандидата](2026-10-30-combined-candidate.md). Исследовательские риски остаются зафиксированы; успешная игра не предполагается заранее, тайминги выключены по умолчанию.

## Global constraints

- Сохранить существующие ключи работающих настроек и проверенную опубликованную базу HR 1.0.5; новые функции по умолчанию сохраняют штатное поведение.
- Кооператив, снятие требований к кроватям, урожайность/рост растений и грибные действия отложены.
- Перед новой версией игры — проверка SHA-512 и актуальных API, затем повтор исследования общих нативных адресов.
- Не менять сохранения вручную, не удалять существующие назначения/сотрудников при уменьшении лимита.
- Резервные DLL хранить вне Mods. Публикация и замена установленной DLL — отдельный шаг после проверки конкретного этапа.
- Компиляция и статические проверки не равны успешной игре. Полноценная реализация таймингов зависит от результата эксперимента, а не от заранее обещанного способа detour.

## Review focus

1. Многоразовое открытие/закрытие и смена сцены: нет накопления подписчиков, строк или блокировки ввода — сценарии задач 1 и 3.
2. Существующий список больше нового лимита, несколько выбранных работников: данные сохраняются и UI не показывает чужой счётчик — задача 1.
3. Купленная после загрузки недвижимость, переезд, лимит ниже занятости, возврат к 0: сохранённые работники не теряются — задача 2.
4. Разный урожай и CurrentWorkSpeed: длительность масштабируется один раз, расход/выход предметов неизменен — задача 4.
5. Общие native RVA, неизвестные/грибные действия, отсутствующий метод: побочные действия сохраняют штатное поведение; отказ изолирован в пределах экспериментальной функции — задачи 0 и 4.
