# Покрытие Work speed по процессам сотрудников

Аудит 30 октября 2026: Schedule I 0.4.7f12 IL2CPP, Steam build 25796331, локальная HR 1.1.0-beta.3, исходники e413211. Исследованы metadata Cpp2IL, фактические native-тела GameAssembly и реализация HR. Игра не запускалась, DLL и предпочтения не изменялись. Это статическая карта покрытия, а не результат игровой проверки.

**Вывод:** Work speed уже влияет на основные действия Handler и Chemist у станций. Однако прежнее описание пропустило общие операции переноса, котёл химика и фиксированные паузы вокруг основных действий. У ботаника покрыты только пять выбранных действий с горшками. Один пункт интерфейса ещё не означает, что одинаково охвачен весь цикл каждой профессии.

В формулах **S** — штатный Employee.CurrentWorkSpeed с игровыми эффектами. У Handler/Chemist HR добавляет к нему свой множитель **M** через WorkSpeedController. У Botanist HR делит только пять выбранных контекстных ожиданий на M; сам WorkSpeedController не меняет. У Cleaner HR заменяет ожидания пяти конкретных корутин на ожидание/M. Все секунды ниже — номинальные секунды действий, не игровые минуты рецепта. Путь, кадры, tick-переходы и наличие ресурсов добавляют своё время.

## Handler / Packager

Порядок задач в Packager.UpdateBehaviour: готовая упаковочная станция → пресс → вывоз output станции → вывоз output пресса → настроенный маршрут. Маршруты и вывоз используют общий MoveItemBehaviour. Отдельной скрытой загрузочной корутины для назначенных станций в этом графе не найдено; снабжение идёт через маршруты/внешнюю логистику.

| Процесс | Реализация и время | Покрытие beta.3 |
| --- | --- | --- |
| Упаковочная станция | PackagingStationBehaviour.MoveNext, RVA 0x942F30: `5 / (PackagingSpeedMultiplier × station.PackagerEmployeeSpeedMultiplier × S)` | Основное рабочее время ускоряется |
| Пресс | BrickPressBehaviour.MoveNext, 0x92D2A0: `15 / (PackagingSpeedMultiplier × S)` | Подготовка ускоряется |
| Завершение прессования | После подготовки: 0.2 с, запуск механики, затем 1 с | Фиксировано; механика отдельно занимает 0.5 + 0.5 с |
| Взятие предмета | MoveItem.GrabItem.MoveNext, 0x943800: `0.5/S`, TakeItem, затем 0.5 с | Взятие ускоряется, завершающая пауза фиксирована |
| Размещение / загрузка / выгрузка | MoveItem.PlaceItem.MoveNext, 0x9448A0: `0.5/S`, перенос в слот, затем 0.5 с | Размещение ускоряется, завершающая пауза фиксирована |
| Дорога к источнику / назначению | MoveNext 0x946B00 / 0x9468E0: запрос пути, 0.5 realtime, ожидание окончания движения | Move speed; начальная пауза относится к запуску навигации и перекрывается с ходьбой |
| Поворот / люк станции | FaceDirection с 0.5 с; люк через deltaTime/HatchLerpTime | Отдельная визуальная механика, не Work speed |

Обычные grab+place дают `1/S + 1` секунд операций плюс путь и переходы. Отдельного длительного пассивного производственного countdown в упаковке и прессе в проверенном графе не найдено: PackSingleInstance и CompletePress непосредственно выполняют завершение. Поэтому формулировка «скорость упаковки не меняется» была бы неверной: она уже меняется.

Доказательства: `artifacts/employee-process-audit-2026-10-30/handler/findings-ru.md`, `handler-native.txt`, `support-native.txt`, воспроизведение `Inspect-Handler.ps1`. Строки handler-native: 7606 (упаковка), 2902 (пресс), 5831/6110 (grab/place); support-native 13427 (механика пресса).

## Chemist

TryStartNewTask выбирает завершение печи → запуск печи → химический стол → котёл → миксер → вывоз готового output этих станций. Готовые продукты химического стола и миксера вывозятся MoveItem; отдельные NPC FinishChemistryStationBehaviour / FinishMixingStationBehaviour среди типов metadata не найдены. Player-only FinishChemistryStationTask не является действием сотрудника.

| Процесс | Рабочее время | Что сейчас ускоряется |
| --- | --- | --- |
| Химический стол, StartChemistryStationBehaviour, 0x945D50 | `1.5 + 8/S + 6/S + 6/S` | Размещение ингредиентов, перемешивание, горелка — 8/6/6. Поворот 0.5 с и подготовка стакана 1 с фиксированы |
| Запуск печи, StartLabOvenBehaviour, 0x944E40 | `2 + 5/S` | Заливка 5/S; поворот/дверь дают фиксированные 0.5 + 0.5 + 1 с |
| Завершение печи, FinishLabOvenBehaviour, 0x92F180 | `3.1 + 10/S` | Основной сбор/обработка 10/S; позиционирование, дверь и пауза после Shatter дают ещё 3.1 с |
| Загрузка/запуск миксера, StartMixingStationBehaviour, 0x945670 | `0.5 + Q/S` | Q итераций по 1/S, где Q — количество партии; поворот 0.5 с фиксирован |
| Запуск котла, StartCauldronBehaviour, 0x942B90 | `15/S` и кадровые yields | Основная ручная подготовка ускоряется; котёл пропущен в прежнем описании |
| Вывоз output | Обычный MoveItem: `1/S + 1`, плюс путь | Взятие/размещение ускоряются, завершающие полсекунды после каждой операции фиксированы |
| Отмена / StopCook / StopAction | Синхронный cleanup пользователя станции, анимации, оборудования и корутины | Собственного рабочего ожидания не найдено |

Корутина химического стола сохраняет `1/S` и использует его для всех 8/6/6. Раннее ожидание 1 с не ускоряется, но это подготовка стакана, а не пропущенный восьмисекундный этап размещения ингредиентов.

Пример при остальных эффектах 1: запуск печи занимает около 7 с при M=1 и `2 + 5/7 = 2.71` с при M=7. Это ускорение рабочего этапа, но не всего цикла в семь раз.

## Cleaner

Порядок задач: готовые мешки → доступный мусор при свободном сборщике → опорожнение полного сборщика → упаковка заполненной урны → ожидание. Подход и перенос мешка — навигация. Найдены четыре профессийных поведения с пятью рабочими корутинами; отдельная шестая корутина работы в этом графе не найдена.

| Действие | MoveNext RVA | Штатные собственные ожидания, с | Покрытие beta.3 |
| --- | --- | --- | --- |
| Подбор мусора | 0x944030 | 0.3 + 0.4 + 0.2 | Все три ожидания делятся на M |
| Упаковка урны | 0x92ED80 | 0.4 + 3 + 0.2 | Все делятся на M |
| Опорожнение сборщика | 0x92E7F0 | 0.3 + 0.4 + N×0.5 + 0.2 | Все делятся на M, включая интервал каждого предмета |
| Поднятие мешка | 0x92E3F0 | 0.3 + 0.2 | Все делятся на M |
| Выкладка мешка | 0x92DF60 | 0.5 + 0.2 | Все делятся на M |

Обычные yields этих пяти тел — WaitForSeconds; скрытого deltaTime-таймера, WaitUntil или вложенной рабочей корутины не найдено. Однако отдельные повороты по 0.5 с, диспетчеризация и скорость анимации не масштабируются этими hooks. Покрытие собственных ожиданий полнее, чем у Handler/Chemist; полного равенства всего цикла множителю всё равно нет.

Опорожнение сборщика физически создаёт предметы над урной; зачисление происходит позже через TrashContainer.TriggerEnter → AddTrash → DestroyTrash. Сокращение N×0.5 меняет интервал появления предметов, но не скорость физики. Это конкретный сценарий для проверки полной/почти полной урны при M=7. Потеря или дублирование не обнаружены: игрового теста не было.

Доказательства: `artifacts/employee-process-audit-2026-10-30/cleaner/findings.md`, `native-annotated-compact.txt`, `supplement-native.txt`, Inspect-Cleaner.ps1 / Inspect-Supplement.ps1.

## Дополнение по Botanist

Прежний разбор охватывал землю, полив, добавки, посадку и сбор из горшка. В beta.3 они читают один множитель. Но полный список работы профессии шире:

- StartDryingRackBehaviour, MoveNext 0x942540: загрузка сушилки использует CurrentWorkSpeed, а HR сейчас не добавляет множитель к этому стеку ботаника — действие вне покрытия.
- StopDryingRackBehaviour, MoveNext 0x942860: выгрузка содержит фиксированное ожидание 0.5 с на шаг; текущий hook её не охватывает.
- UseSpawnStationBehaviour, MoveNext 0x943370: работа на станции спавна `6/S`, но HR-множитель ботаника в S не включён.
- Нанесение спавна и сбор грибов наследуют GrowContainerBehaviour; MistMushroomBed наследует WaterPotBehaviour. Общая PerformAction делит время на CurrentWorkSpeed, но Classify в HR принимает только пять точных типов горшковых действий. Грибные типы остаются вне множителя.
- Получение расходников GrowContainerBehaviour.GrabRequiredItemFromSupplies, MoveNext 0x943C70, содержит две фиксированные паузы по 0.5 с и не охвачено hook на PerformAction.

Это границы реализации, а не обнаруженные сбои исполнения. Единый Work speed позволяет упростить будущую реализацию: проверить перевод ботаника на собственную multiplicative-запись штатного WorkSpeedController, как у Handler/Chemist, вместо деления пяти ожиданий. При переходе старое деление обязательно убрать, иначе получится M². Загрузка сушилки/станция спавна и общие GrowContainer-действия имеют штатную точку подключения; фиксированные паузы всё равно потребуют отдельного решения.

Доказательства: `artifacts/employee-process-audit-2026-10-30/botanist-additional-inventory.txt`, `botanist-additional-native.txt`, `Inspect-BotanistCoverage.ps1`; текущие BotanistTimingPolicy.Classify и EmployeeSpeedController.Apply.

## Порядок дальнейшей доработки

1. Сохранить два пункта UI. Для ботаника проверить общий native WorkSpeedController и расширить покрытие без второго применения множителя; добавить проверки сушилки, станции спавна и грибных действий.
2. Разделить фиксированные паузы на рабочие восстановительные и синхронизирующие. Кандидаты: post-transfer 0.5 у Handler/Chemist, подготовка стакана у Chemist. Точные MoveNext states записаны в приложенных отчётах. Только после проверки анимации/порядка ресурсов решать, какие паузы делить на M.
3. Для двери/подноса/разбивания печи, пресса и поворотов исследовать связанные длительности. Ускорение только wait может закончить действие раньше механики. Секунда пресса соответствует двум фазам по 0.5 с, поэтому её нельзя автоматически считать лишней задержкой.
4. Сохранить навигационную стабилизацию, ожидание прибытия, общий tick и автоматические рецепты. Они не становятся рабочими таймерами только потому, что сотрудник их ожидает.
5. Проверить законченные циклы в одиночной игре: M=1/2/7/0.5, повторное сохранение, отмена, заполненный output, частичная вместимость, одинаковое количество продукта. Для Cleaner отдельно проверить физический перенос содержимого в урну.

Реализация расширений в рамках аудита не выполнялась. Установленная beta.3 сохранена с SHA256 `8AB4D685126CA574BC9AB89BBBAA4E9762B744A903FC2B94BC5454B606F28BE4`. Автоматические тесты прошлой сборки не доказывают игровое покрытие или безопасное сокращение найденных пауз.

Границы: фактические animation clips, сериализованные UnityEvent listeners, prefab-множители и физическое поведение не измерялись; произвольные ITransitEntity, боевые/аварийные NPC-состояния и внутренности pathfinding не проходили рекурсивный аудит. Native RVA aliases сами по себе не доказывают тип вызова; использованы также поля, константы, выделяемые type-info и поток управления.
